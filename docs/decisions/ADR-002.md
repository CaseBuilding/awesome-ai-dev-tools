# ADR-002: First-Seen Tracking for New Repo Detection

## Status
Accepted

## Date
2026-06-01

## Context
需要在新项目入库时自动标记 🆕，并在 7 天后自然消失。约束条件：

- **初始数据不标 🆕** — 存量 498 个 repo 不能全部显示"新"
- **增量更新可检测** — 下次 fetch 新增的 repo 要自动标 🆕
- **自动过期** — 超过 7 天自然消失，不需要手动清理
- **零手动维护** — 不依赖人工标记"这是新的"

## Decision
引入 `data/first_seen.json`，记录每个 repo 的首次入库日期，配合 `_baseline` 基线日期做判断。

### 数据格式
```json
{
  "_baseline": "2026-06-01",
  "roboflow/supervision": "2026-06-01",
  "Wan-Video/Wan2.2": "2026-06-05"
}
```

### 判断逻辑
```
first_seen === _baseline    → 存量项目，不标 🆕
first_seen !== _baseline    → 后续新增
  last_updated - first_seen ≤ 7 天 → 🆕
  last_updated - first_seen > 7 天 → 过期消失
```

### 谁写入
- **`scripts/fetch-repos.js`**：发现新 repo（在 newRepos 但不在 existingRepos 中），写入 today 日期
- **首次运行**：自动初始化 `_baseline` 为当天日期
- **存量数据初始化**：通过手动脚本将所有 repo 标为 baseline 日期

### 谁读取
- **`scripts/generate-readme.js`**：读取 first_seen.json，生成 README 时判断是否标 🆕

## Alternatives Considered

### 方案 A：在 repos.json 中直接加 `first_seen` 字段
- Pros：不需要额外文件
- Cons：repos.json 是自动生成的，每次 fetch 会全量覆盖，需要在写入时保留 first_seen 字段，耦合度高
- Rejected：分离到独立文件，职责清晰

### 方案 B：用 git commit 时间判断
- Pros：零数据文件
- Cons：repos.json 是自动生成的，每次提交都会更新 last_updated，无法区分"项目入库"和"数据重跑"
- Rejected：粒度不够

### 方案 C：纯日期比较（无 baseline）
- Pros：最简单
- Cons：初始数据全部标 🆕，第一周 README 被 🆕 淹没
- Rejected：用户体验差

## Consequences
- `_baseline` 机制让首次部署零噪音
- 后续入库自动标记，7 天后自动消失
- 新增文件维护成本低（约 30KB，纯 JSON）
- 已知限制：repo 被删除后重名重建，旧 first_seen 不会自动清除（概率极低，已在代码中加注释说明）
- 窗口期受 pipeline 频率影响，实际有效期为 7 + pipeline_interval 天（上次 doubt-driven review 发现，接受为 trade-off）

## Doubt-Driven Review
本决策和实现经过了 `doubt-driven-development` 对抗性审查，发现并修复了 3 个问题：
1. `_baseline` 无代码写入 → 修复：fetch-repos.js 自动初始化
2. 首次运行无 baseline → 同上修复
3. 所有错误静默失败 → 修复：加 console.warn 日志
